---
title: Include modules in code coverage
description: Add the code of the enabled modules to the source list of phpunit.xml so that the coverage report includes it.
---

import { Steps } from '@astrojs/starlight/components';

At the end, the coverage report of your application includes the code in `Modules/Blog/app`. Prerequisites: a `phpunit.xml` in the application root, a `modules_statuses.json` that lists the modules, and a coverage driver (Xdebug or PCOV).

<Steps>

1. Update `phpunit.xml`.

   ```bash
   php artisan module:update-phpunit-coverage
   ```

   The command reads `modules_statuses.json`, the file set in `modules.activators.file.statuses-file`. For each enabled module that has an `app` folder, it adds an entry to `<source><include>`. It keeps the formatting of the file.

   ```xml title="phpunit.xml"
   <source>
       <include>
           <directory>app</directory>
           <directory suffix=".php">./Modules/Blog/app/</directory>
       </include>
   </source>
   ```

   The command also removes the entries of modules that are disabled or deleted. If `<source>` has no `<include>`, the command creates one with `<directory>./app</directory>` and the module entries. This includes an empty `<source></source>` or `<source/>`. An empty `<include/>`, `<include />` or `<include></include>` on its own line inside `<source>` gets the module entries only. With `<source>` and `<include>` on the same line, such as `<source><include/></source>`, the command prints `Could not find where to add the module entries in phpunit.xml: add them by hand.`, leaves the file unchanged and exits 0. The command prints `phpunit.xml updated with enabled module directories.` when it placed the entries. When it cannot find where to add them, it prints a warning, leaves the file unchanged and prints no success line.

2. Run the tests with coverage.

   ```bash
   php artisan test --coverage
   ```

   Without a coverage driver mode, the run prints `ERROR  Code coverage driver not available. Did you set Xdebug's coverage mode?` and exits with status 1. With Xdebug, set its mode for the run:

   ```bash
   XDEBUG_MODE=coverage php artisan test --coverage
   ```

</Steps>

Run the command again after you enable, disable, add or delete a module. The module tests must be in a test suite: see [Run the tests of a module](/laravel-modules/guides/testing/run-module-tests/).

### Check the result

Open `phpunit.xml` and look for the `Modules/Blog/app` entry. The coverage report lists file paths under `Modules/Blog/app`, not namespaces.

If the command fails, its exit status tells why: `100` no `phpunit.xml`, `99` no statuses file, `97` empty or invalid XML in `phpunit.xml`, `98` the command cannot decode the statuses file. That happens when the file is empty or holds only whitespace, which the file activator accepts at boot, or when the file holds invalid JSON and the active activator is not `FileActivator`, so nothing else reads the file. With a custom activator and a valid file, the command succeeds. With `FileActivator` and non-empty invalid JSON, the application fails at boot with an `InvalidJsonException` and exit status 1.
